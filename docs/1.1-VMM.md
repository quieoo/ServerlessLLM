# VMM 显存池实验

`1.1-overall_vmm.sh` 使用 CUDA Virtual Memory Management (VMM) 管理物理显存页。权重和 KV Cache 从同一个每 GPU physical-page pool 分配；每次新的模型加载开始前，当前模拟器会回收旧 KV Cache，并在空间不足时优先驱逐非当前模型的缓存权重。

VMM 后端保留 tensor group/fingerprint 的参数缓存语义：一个 tensor group
对上层表现为连续的虚拟地址，但其底层可以由任意空闲物理页组成。模型每次
`LoadModel` 后重新获得参数地址，因此权重被驱逐时可以释放 VA 与物理页，
下次加载时重新建立映射。

当前实现采用了以下性能优化：

1. **CUDA Runtime 预热**：初始化每张 GPU 时执行 `cudaSetDevice` 和
   `cudaFree(nullptr)`，提前创建 primary context，避免首个模型请求承担
   CUDA Runtime 初始化时间。
2. **预创建物理页池**：启动时按照 `-g/--gpu-pool` 指定的容量，通过
   `cuMemCreate` 预创建全部 physical pages。默认页大小使用
   `cuMemGetAllocationGranularity(..., CU_MEM_ALLOC_GRANULARITY_MINIMUM)` 的
   返回值，也可以通过 `--vmm_page_size_mb` 设置为原生粒度的 2 次幂倍数；
   请求热路径不再执行 `cuMemCreate/cuMemRelease`。
3. **O(1) 物理页分配**：空闲 physical handle 保存在 free-list 中，权重和
   KV 都通过栈式 pop/push 获取和归还页面，避免扫描显存 region 或运行
   bin-packing/碎片合并算法。
4. **连续 VA、离散物理页**：每个 tensor group/KV allocation 只预留一段
   连续 VA，再将多个独立 physical pages 映射到其中。只要总空闲页足够，
   就不会因为缺少连续物理区间而失败，也不需要搬移已有参数来整理碎片。
5. **批量设置访问权限**：一个 allocation 的物理页映射完成后，只对整个
   连续 VA 区间调用一次 `cuMemSetAccess`，而不是逐页设置权限。
6. **只映射 cache miss**：命中的 tensor group 直接复用已有 VA，完全命中
   的模型请求不会产生新的 `cuMemMap`；日志中的 `cached_bytes`、
   `to_load_bytes` 和 `map_pages` 可用于核对命中与映射开销。
7. **cache-affinity 多 GPU 调度**：优先选择目标模型缓存字节数最多的 GPU；
   缓存量相同时选择空闲页更多的 GPU，再以 GPU ID 保证确定性，减少跨卡
   重复加载和不必要的权重驱逐。
8. **成本感知权重驱逐**：显存不足时，根据历史访问次数和模型加载敏感度
   选择冷权重释放，同时保护当前正在加载/运行模型的 tensor groups。
9. **权重/KV 统一容量与 KV 优先**：模型切换时先回收旧模型 KV；为当前
   模型分配 KV 时，可以回收非当前模型的缓存权重，使 KV 不受固定分区比例
   限制。权重和 KV 的占用都计入同一个 physical-page pool utilization。

## VMM vs Legacy

### 不合并 Tensor 的固定页空间放大

`tensor_page_amplification.py` 读取配置中每个模型的
`rank_0/tensor_meta_index.json`。每个 tensor 独立按照
`ceil(tensor_bytes / page_bytes)` 分配固定大小的页；不读取
`tensor_group_index.txt`，也不调用 `MergeTGsRatio`。输出包括每个模型及所有
模型汇总的逻辑空间、映射空间、页内浪费和空间放大倍数。

```bash
cd /mnt/n0/Tangram/Tangram

python tools/mock_allocation/tensor_page_amplification.py \
  --config configs/servegen_8_models.json \
  --page-sizes-mib 2 4 8 16 32 64 128 256 \
  --json-output docs/1.1-tensor-page-amplification.json \
  | tee docs/1.1-tensor-page-amplification.log
```

这里的空间放大定义为：

```text
amplification = sum(ceil(tensor_bytes / page_bytes) * page_bytes)
                / sum(tensor_bytes)
```

该结果只反映“每个 tensor 独占整数页”的静态页内碎片，不包含 KV Cache、
模型间 fingerprint 复用、运行时驱逐，以及多个 tensor 共享同一页的 packing。

如需同时统计旧 `Allocateion` 的 `MergeTGsRatio(40)` 后 group 数量，增加
`--merge-tensor-groups`。脚本会读取 `tensor_group_index.txt` 并将相邻 tensor
groups 合并到目标约 40 组，但空间仍严格按每个 tensor 独占整数页计算；
不同 tensor 不会共享同一个 page。因此 merge target 只影响 group 数量统计，
不会改变本脚本报告的 page 空间放大：

```bash
cd /mnt/n0/Tangram/Tangram

python tools/mock_allocation/tensor_page_amplification.py \
  --config configs/servegen_8_models.json \
  --page-sizes-mib 2 4 8 16 32 64 128 256 512 \
  --merge-tensor-groups \
  --json-output docs/1.1-tensor-group-page-amplification.json \
  | tee docs/1.1-tensor-group-page-amplification.log


```

`--merge-tensor-groups` 不带值时目标组数为 40；例如
`--merge-tensor-groups 80` 可以改为目标约 80 组。需要注意，当前真实 VMM
backend 的 `MapWeight(group.size)` 是按合并后的 group 分配页，允许 group 内
相邻 tensor 共享边界 page；因此该脚本现在表达的是更严格的
tensor-exclusive placement，而不是 backend 当前 packing 行为。

#### 总体结果
| 方案 | 平均延迟 | p50 | p95 | p99 | 完整命中 |
| ---- | -------- | ---- | ---- | ---- | -------- |
| Legacy | 139.422 ms | 0.231 ms | 701.717 ms | 1256.789 ms | 663 / 1000 |
| VMM 2 MiB | 260.818 ms | 0.049 ms | 1321.508 ms | 2215.861 ms | 671 / 1000 |
| VMM 64 MiB | 165.420 ms | 0.062 ms | 705.441 ms | 1202.535 ms | 530 / 1000 |

#### 核心结论
1. 2 MiB VMM 比 Legacy 平均慢 87.1%。
2. 64 MiB VMM 比 2 MiB VMM 快 36.6%。
3. 64 MiB VMM 与 Legacy 延迟水平接近，但平均延迟仍高 18.7%。
4. 64 MiB VMM 的 p95 基本等于 Legacy，p99 甚至比 Legacy 低 4.3%。
5. VMM 完整缓存命中延迟显著更低：约 0.05–0.06 ms；Legacy 完整命中延迟为 0.231 ms。

#### 缓存与加载量
1000 个请求对应的理论模型权重访问总量约为 14.791 TB。

| 方案 | 缓存字节比例 | 实际加载量 |
| ---- | ------------ | ---------- |
| Legacy | 76.92% | 3.413 TB |
| VMM 2 MiB | 75.69% | 3.596 TB |
| VMM 64 MiB | 72.70% | 4.039 TB |

##### 关键现象分析
- 2 MiB VMM 缓存效果与 Legacy 接近，实际加载量仅比 Legacy 多 5.3%。
- 64 MiB VMM 加载量相比 Legacy 增加 18.3%，完整命中次数由 663 次下降至 530 次。
- 即便 64 MiB VMM 需要拷贝更多权重，整体性能仍远优于 2 MiB VMM。
- 64 MiB 页缓存缓存效率下降根源：每个 Tensor Group 空间需向上对齐至 64 MiB。日志显存利用率看似接近 100%，但其中包含大量页内闲置空间，可用于缓存权重的有效容量低于 Legacy、2 MiB VMM 方案。

销毁前 VMM 地址始终有效。

### 代码修改

1. `tools/mock_allocation/src/vram_manager_binding.cpp`：增加查询 VMM resident
   tensor 数量、group base、offset 和 size 的 C ABI。
2. `tools/mock_allocation/src/vram_manager_vmm.h`：增加 `TensorBinding` 查询；
   `reuse_granularity=-1` 保留 checkpoint 原始 tensor groups，避免 mock
   simulator 的 group 合并改变真实 tensor offset。
3. `tools/mock_allocation/src/tangram_vmm_torch.cpp`：使用 `torch::from_blob`
   将 VMM CUDA pointer 包装成 non-owning CUDA Tensor。
4. `ElasticKV/vllm/model_executor/model_loader/tangram_vmm.py`：在 worker 内创建
   VMM pool、注册/加载 `rank_0` checkpoint、恢复 state dict。
5. `ElasticKV/vllm/model_executor/model_loader/loader.py`：设置
   `TANGRAM_VMM_IN_PROCESS=1` 时选择同进程 VMM loader；否则保持原有 Store
   loader 行为。
6. `ElasticKV/vllm/engine/llm_engine.py`：同进程 VMM 模式跳过旧 Store GPU
   pool IPC handle 查询，KV cache 使用 vLLM 默认分配路径。

## 1000 次多模型切换后的同模型推理实验

### 实现

`tools/mock_allocation/vllm_vmm_switch_bench.py` 将 VMM session 提升为进程级
共享 `TangramVmmPool`：

1. 根据 `configs/servegen_8_models.json` 注册 trace 使用的 8 个模型。
2. 初次加载目标模型 `model_id=0`（Qwen2 3B），创建 vLLM engine，warmup 后
   测量相同请求 10 次。
3. 销毁 vLLM engine 和默认 KV cache，但保留 VMM manager、physical-page
   pool、模型 fingerprint cache 和 host checkpoint cache。
4. 按 `evaluation/traces/servegen_tangram.trace` 前 1000 条记录调用共享 pool
   的 `LoadModel`。切换阶段不创建其他模型的 vLLM engine，只执行真实 VMM
   映射、命中、驱逐和 H2D copy。
5. 再次加载同一个目标模型，创建同配置 vLLM engine，对完全相同请求测量
   10 次 Prefill 和 Decode。

VMM backend 新增 `tangram_vram_model_layout`，记录以下布局代理：

- `page_count`：模型占用的 VMM physical extent 数量。
- `contiguous_runs`：按模型虚拟访问顺序，相邻 extent creation ID 连续的
  run 数量。
- `adjacent_breaks`：相邻页面的 extent ID 不连续次数。
- `extent_id_span`：最大与最小 extent ID 的跨度。
- `span_ratio=extent_id_span/page_count`：大于 1 表示页面散布在更宽的 pool
  ID 范围内。

这些 ID 是 `cuMemCreate` physical handle 的创建顺序，只是物理布局分散度
代理。CUDA VMM API 不提供真实 GPU physical address，因此不能把 extent ID
直接称为物理地址。

### 结果解释与下一步

这次实验强力支持“切换后参数 extent 布局更分散”，但没有观察到与布局变化
同等量级的计算性能下降。中位数上 scheduled Prefill 慢 1.19%、Decode/token
慢 2.08%，属于弱退化；TTFT 中位数没有变慢。

不能使用均值宣称切换后更快。初始阶段前四个样本明显受 GPU 频率、kernel
和 allocator 热身影响：初始 Decode/token 前三个样本约 20 ms，稳定后约
12.4 ms；切换后样本集中在 12.49--12.96 ms。`--warmup 2` 不足以消除初始
离群值。

下一轮建议：

1. 把 `--warmup` 提高到 10 或 20，再重复完整实验。
2. 至少运行 3 个独立进程/随机化初始与切换后测量顺序，报告置信区间。
3. 固定 GPU application clocks，避免长时间 H2D workload 改变频率和温度。
4. 增加 128/512/2048 prompt token 的 Prefill 扫描；短 prompt 容易被调度与
   Python 开销淹没。
5. 增加不打散的 VMM layout policy 作为对照，否则当前只能建立相关性，不能
   单独证明 extent 分散导致约 1--2% 的退化。

## 2026-07-21：VMM Run 接入 ODKV

### 实现范围

本次按推荐顺序完成了 VMM-backed ODKV 的最小闭环：

1. `VmmGpuPagePool` 为 KV 预留固定、连续的 VA arena，但不预占额外物理页；
   KV logical block 首次出现时，才从权重共用的 physical-page pool 中取页并映射。
2. segmented kernel 收到固定 `kv_base` 和相对 offset，不再把 `MapKV` 返回的
   绝对 CUDA VA 误当成 offset。
3. 增加 `tangram_vram_kv_base/available_blocks/allocate/release/clear` C ABI；
   KV 分配时保护当前模型的全部 tensor group，只允许驱逐其它模型的缓存权重。
4. `TangramVmmKVProvider` 将 vLLM logical block ID 映射到 VMM offset；
   `AsyncBlockManager` 可以在 Store provider 和 in-process VMM provider 之间选择。
5. `LLMEngine` 使用显式 `TANGRAM_KV_BACKEND=vmm` 激活 external KV。worker
   不创建原生 `gpu_cache` tensor，仍设置 scheduler 的 logical block 数量并执行
   cache size 检查。
6. 将 segmented table 拆为两张：全局 logical-ID write table 供
   `reshape_and_cache_segment` 使用；逐 sequence compact table 供
   `segmented_attention_v1` Decode 使用。

### 当前限制与待确认项

1. 只支持当前实验的单进程、单 GPU `GPUExecutor`。Ray 或多进程 worker 不能
   直接访问 Python 进程内的 `_SHARED_POOL`。
2. 必须使用 xFormers segmented backend 和 eager 模式；CUDA Graph 尚未接入
   新增的 write table。
3. 当前不支持 KV swap、prefix caching、beam-search block copy 和 speculative
   decoding；建议保持 greedy decoding、单序列请求。
4. 当前代码强制 `cache_config.block_size=32`。Qwen2-14B 为 48 层、8 KV heads、
   head size 128、FP16，因此一个完整跨层 KV block 是 6,291,456 bytes（6 MiB）；
   128 blocks 需要约 768 MiB。仍应在实际日志中核对 provider 报告的 available
   blocks，因为 VMM page size 和 pool 中残留权重会影响最终容量。
5. `segmented_attention_v1` 的 Qwen2-14B head-size/block-size 模板是否完整，必须
   由上面的 kernel smoke 和首次短模型 smoke 实测确认。
6. 本版是 first-touch mapping，不是逐请求物理页归还。若后续研究权重与 KV
   在并发请求结束时动态竞争页面，需要继续接 scheduler free event。

## 2026-07-21：Qwen2-14B VMM + ODKV 实测结果

结果文件：

- `docs/1.1-vllm-vmm-odkv-qwen2-14b-1000.json` / `.log`
- 对照：`docs/1.1-vllm-exclusive-qwen2-14b.json` / `.log`

### 配置与 ODKV 激活验证

两组使用相同的 Qwen2-14B、FP16、GPU 0、warmup 10、测量 10 次、固定 seed
生成的 8,000 字符 prompt（实际 906 tokens）、128 output tokens 和 128 logical
GPU blocks。两组最终输出文本一致。

VMM 组的 JSON 明确记录 `kv_backend=vmm`。日志还有更直接的运行时证据：

```text
[AsyncBlockManager] Init with block size: 6291456
Overriding num_gpu_blocks=2091 with num_gpu_blocks_override=128
# GPU blocks: 128, # CPU blocks: 682
...
reclaimed_kv_bytes=207618048
```

一个 Qwen2-14B 跨层 KV block 是 6,291,456 bytes；207,618,048 bytes 正好是
33 blocks。906-token Prefill 和 128-token Decode 总共触达
`ceil((906 + 128) / 32) = 33` blocks。因此这次运行确实按需从 VMM pool 映射了
KV blocks，并在随后的模型加载时回收，没有回退到默认 vLLM KV tensor。

日志未发现 Traceback、RuntimeError 或 CUDA error。只有模型配置从 BF16 转为本次
实验指定 FP16 的提示。

### 权重布局与切换

VMM 重放 1,000 个 load requests，其中 703 次相邻请求发生模型切换，耗时
526.348 秒。目标模型权重布局变化如下：

| 布局代理 | 初始 | 1000 requests 后 |
|---|---:|---:|
| page count | 14,206 | 14,206 |
| contiguous runs | 1 | 13,752 |
| adjacent breaks | 0 | 13,751 |
| extent ID span | 14,206 | 20,480 |
| span ratio | 1.000 | 1.442 |

目标权重从单一 extent run 变成接近逐页断开的布局。切换结束时目标模型已不在
cache；测量前重新加载了完整 29,540,067,328 bytes，随后 engine 内的再次绑定为
full hit。参数加载发生在推理计时之前。

### 与 native exclusive 的推理对比

以下使用 10 次测量的中位数；括号为相对 native exclusive 的变化：

| 指标 | Native exclusive | VMM+ODKV 初始 | VMM+ODKV 切换后 |
|---|---:|---:|---:|
| scheduled Prefill | 230.891 ms | 231.196 ms (+0.13%) | 233.275 ms (+1.03%) |
| TTFT | 233.968 ms | 233.982 ms (+0.01%) | 237.523 ms (+1.52%) |
| Decode/token | 42.542 ms | 43.816 ms (+3.00%) | 43.987 ms (+3.40%) |
| Decode total | 5,402.793 ms | 5,564.623 ms (+3.00%) | 5,586.399 ms (+3.40%) |
| E2E | 5,637.666 ms | 5,799.874 ms (+2.88%) | 5,824.468 ms (+3.31%) |

均值给出相同方向：VMM+ODKV 初始/切换后相对 exclusive 的 Decode/token 分别
慢 2.84%/3.50%，E2E 分别慢 2.72%/3.44%。因此主要差距稳定地出现在 Decode，
不是 Prefill。

只比较同一次 VMM+ODKV 实验的切换后与初始阶段：

| 指标 | 初始中位数 | 切换后中位数 | 变化 |
|---|---:|---:|---:|
| scheduled Prefill | 231.196 ms | 233.275 ms | +0.90% |
| TTFT | 233.982 ms | 237.523 ms | +1.51% |
| Decode/token | 43.816 ms | 43.987 ms | +0.39% |
| E2E | 5,799.874 ms | 5,824.468 ms | +0.42% |

### 结论与解释边界

1. VMM-backed ODKV 已正确激活，且输出与 native exclusive 一致。
2. 初始连续权重布局下，Prefill/TTFT 与 exclusive 几乎相同；ODKV 路径的主要
   成本体现在 Decode，约为 3%。这更可能来自每个 Decode step 使用
   `segmented_attention_v1` 和 offset table，而不是权重布局本身。
3. 1,000 次切换将权重 extent 显著打散，但在 VMM+ODKV 内部只进一步造成
   Decode/token +0.39%、E2E +0.42% 的中位数退化。当前结果仍不支持“权重页面
   分散会让真实 LLM 推理慢一到两倍”。
4. TTFT 的切换后退化为 +1.51%，高于 scheduled Prefill 的 +0.90%，说明仍有
   scheduler、同步或运行状态噪声，不能全部归因于权重物理页分散。
5. exclusive 使用 native safetensors、普通权重 allocation 和默认 paged KV；
   VMM+ODKV 使用 Tangram fused checkpoint、VMM 权重和 segmented KV。因此二者
   约 3% 的 Decode 差距是整条路径差异，不能仅归因于 ODKV。若要隔离 ODKV，
   应在同一 VMM 权重布局上直接比较 `--kv-backend default` 与
   `--kv-backend vmm`。
6. `engine_init_ms` 不可用于 exclusive/VMM 加载速度对比：VMM benchmark 在开始
   engine 计时前已经显式完成目标参数加载，而 exclusive 的 engine 计时包含原生
   safetensors 加载。

当前最重要的后续对照是保持模型权重、prompt、测量顺序和切换 trace 完全相同，
只切换 KV backend。这样可以把约 3% 的 Decode 差距拆成 segmented ODKV kernel
成本与其它 checkpoint/权重加载差异。
